# Migration: v1.20.4

**Previous version:** 1.20.3
**Target release version:** 1.20.4
**Status:** released

> **To operators:** This document describes the schema and configuration changes for
> **Data Manager v1.20.4**. Apply these migrations when upgrading from v1.20.3 to v1.20.4.
>
> This is a **security patch release**. It carries two additive tables and a behaviour change to
> the login, registration and account-recovery flows. **No table, column or index is altered or
> dropped**, and no migration in this release destroys data. Read the *Release-wide pre-flight*
> and the *Recommended upgrade sequence* before you begin.

For the migration documentation structure, see [`README.md`](../README.md).

---

## Read this first — what changes for users

Three changes are visible to people using the platform. None of them is optional, and two of them
**require the helpdesk to be briefed before the deploy**.

1. **Confirmation and password-reset links already in inboxes stop working.** The old links carried
   the user id as the credential; the new ones carry a single-use token. There is no compatibility
   window (decision B1). This is deliberate and is the point of the release.
2. **Repeated failed logins and repeated "resend" clicks are now blocked server-side** and survive a
   page reload. Previously the resend lockout was a 30-second client-side timer that a reload reset.
3. **A visitor is never told they are being throttled.** A throttled login produces the same
   "Incorrect username or password" as a wrong password.

The helpdesk text for (1) and (3) is in *Operator notes* under each migration. **#1712** tracks the
wider communication.

---

## Why this release follows 1.20.3 so closely

**1.20.3 contains no auth migrations, and that is expected.** It was cut from `main` before the
hardening branch was merged, so it carries six unrelated fixes (RO-Crate export, openBIS retry
deadlines, sample write ordering, comment-length validation) and **none** of the tables below.

If you run 1.20.3 and the pre-flight check says `user_verification_token` does not exist, nothing is
wrong with your installation — that is the correct state, and this release applies the tables for the
first time. The same is true on 1.20.2.

The security work is a single unit: the tokenised-link code, the throttling code and the two tables
have to arrive together, because each table is queried on the first request that needs it. That is
why it was not split across two release cuts.

## Release-wide pre-flight

The migration scripts referenced by this guide are shipped alongside it in
[`v1.20.4/`](v1.20.4/) and are the copies to run.

Before applying any migration:

1. **Back up the `data_management` database.** Both migrations are additive and neither destroys
   data, so a backup is insurance rather than a requirement — but a failed `CREATE TABLE` part-way
   through is easier to reason about with one.
   ```bash
   mysqldump -u <user> -h <host> -P <port> data_management \
       > backup-data-manager-v1.20.3.sql
   ```
2. **Confirm connectivity** to the `data_management` datasource. Both tables belong to it; there is
   **no `finance` datasource change** in this release.
   ```sql
   SELECT DATABASE();
   -- Expected: data_management (or whatever your DM schema is named)
   ```
3. **Confirm charset / collation**, which the `auth_attempt` unique key depends on.
   ```sql
   SELECT @@character_set_database AS charset,
          @@collation_database    AS collation;
   -- Expected: utf8mb4, utf8mb4_unicode_ci
   ```
4. **Confirm your deployment's schema baseline.** This release targets **v1.20.3**. If you are
   jumping from **1.19.x or earlier**, apply [`v1.19.0.md`](v1.19.0.md) **first**, in version order —
   its migration #2 is stop-the-world and cannot be combined with this release's window.
   If you are already on **1.20.3**, note that release contained **no auth migrations**: `1.20.3` was
   cut from `main` before the hardening landed. Both tables below are therefore absent on your
   installation, exactly as on 1.20.2, and the pre-flight checks will confirm it.
5. **Locate your configuration source.** This release renames two property keys and two environment
   variables, and **Spring Boot does not fail on unknown keys** — a deployment still carrying the old
   names starts cleanly and silently ignores them. See *Application properties changes*.
6. **Brief the helpdesk** before the deploy. Scripts are in the operator notes for both migrations
   and under *Read this first*.

### Recommended upgrade sequence

The order matters, and both migrations must precede the code deploy.

| Step | Action | Notes |
|---|---|---|
| 1 | Announce the window | Links in flight stop working at step 4, not at step 2 |
| 2 | Back up `data_management` | Step 1 above |
| 3 | Apply **migration #1** (`auth-flow-hardening.sql`) | Additive; safe with the application running |
| 4 | Apply **migration #2** (`auth-attempt-throttling.sql`) | Additive; safe with the application running |
| 5 | Rename the two property keys / env vars | Skipping this silently disables nothing visible — but see the warning |
| 6 | Deploy the v1.20.4 application code | Rolling restart; no data migration to wait for |
| 7 | Run the *Post-migration checklist* | Includes the functional smoke tests |

**Why the schema comes first.** Both tables are queried on the first request that needs them, and
both failure modes are bad in different ways:

| Missing table | Consequence |
|---|---|
| `user_verification_token` | No link can be issued or consumed — and the failure is **silent**: registration appears to succeed, but no link works |
| `auth_attempt` | **Login fails outright** — the throttle is consulted before authentication |

**Do not deploy the code first.** Unlike the migrations, that failure is immediate and total.

## Application properties changes

> **Read this before upgrading.** This release renames two configuration keys and changes two
> defaults. Spring Boot does **not** fail on unknown environment variables or unknown properties, so
> a deployment carrying the old names will start cleanly and silently ignore them. Nothing warns you.

### Renamed keys — old names are now ignored

| Removed | Replacement | Notes |
|---|---|---|
| `routing.email-confirmation.confirmation-parameter` | `routing.email-confirmation.token-parameter` | same meaning, new name |
| `routing.password-reset.reset-parameter` | `routing.password-reset.token-parameter` | same meaning, new name |
| `EMAIL_CONFIRMATION_PARAMETER` (env) | `EMAIL_CONFIRMATION_TOKEN_PARAMETER` | env var renamed |
| `PASSWORD_RESET_PARAMETER` (env) | `PASSWORD_RESET_TOKEN_PARAMETER` | env var renamed |

### Changed defaults

| Key | Old default | New default | Why |
|---|---|---|---|
| `routing.email-confirmation.endpoint` | `/login` | `/registration/confirm` | confirmation moved off `/login` so it no longer mutates state on GET |
| `routing.password-reset.endpoint` | `new-password` | `/registration/new-password` | the old default was a bare, non-navigable path |

**If your deployment explicitly sets either endpoint to the old value**, links will point at routes
that no longer consume tokens. They will appear broken — and for a different reason than the
intentional link-format change, which will make it harder to diagnose. Check both.

### New keys (all have working defaults)

| Key | Default | Bound |
|---|---|---|
| `qbic.verification-token.confirmation-lifetime` | `PT1H` | max `PT1H` (AUTH-R-05) |
| `qbic.verification-token.reset-lifetime` | `PT5M` | max `PT15M` (AUTH-R-05) |
| `qbic.verification-token.set-password-lifetime` | `PT1H` | max `PT1H` (AUTH-R-05) |

Values are ISO-8601 durations (`PT1H`, `PT5M`, `PT30M`).

⚠️ **An out-of-bound value is a startup failure, not a silent weakening.** The service validates
these in its constructor and refuses to boot if a configured lifetime exceeds the AUTH-R-05 maximum.
Setting `VERIFICATION_RESET_LIFETIME=PT30M` will stop the application from starting. Shorter values
are always allowed.

### Throttle thresholds (new, all have defaults)

| Property | Env var | Default | Meaning |
|---|---|---|---|
| `qbic.auth-throttle.login.max-attempts` | `AUTH_THROTTLE_LOGIN_MAX_ATTEMPTS` | `10` | failed logins allowed per window |
| `qbic.auth-throttle.login.window` | `AUTH_THROTTLE_LOGIN_WINDOW` | `PT15M` | counting window |
| `qbic.auth-throttle.login.block-duration` | `AUTH_THROTTLE_LOGIN_BLOCK_DURATION` | `PT15M` | how long a block lasts |
| `qbic.auth-throttle.resend.max-attempts` | `AUTH_THROTTLE_RESEND_MAX_ATTEMPTS` | `3` | resends allowed per window |
| `qbic.auth-throttle.resend.window` | `AUTH_THROTTLE_RESEND_WINDOW` | `PT15M` | counting window |
| `qbic.auth-throttle.resend.block-duration` | `AUTH_THROTTLE_RESEND_BLOCK_DURATION` | `PT15M` | how long a block lasts |

A non-positive `max-attempts`, window or block-duration is a **startup failure**, not a silent
no-op — the same fail-fast posture as the verification-token lifetimes.

### Deployment checklist for the properties

1. Apply both SQL migrations **first** — see *Recommended upgrade sequence*.
2. Rename the two environment variables (or the two property keys) in the deployment configuration.
3. Check whether `EMAIL_CONFIRMATION_ENDPOINT` / `PASSWORD_RESET_ENDPOINT` are overridden, and update
   them if they point at the old routes.
4. Decide whether to keep the default lifetimes and throttle thresholds. No action is needed to
   accept them.
5. **Use `application.properties.template` as the reference** — it is the single source of truth for a
   working configuration, and it lists every value explicitly.

## Migration #1: Auth-flow hardening — verification tokens

**Status:** ✅ **approved and promoted.** The AGENTS.md §12 schema-change sign-off was recorded, the
script moved to `sql/migrations/`, and its `CREATE TABLE` block was added to
`sql/complete-schema.sql` so a fresh install matches an upgraded one.

| Field | Value |
|---|---|
| **Story** | [`FEAT-AUTH-FLOWS-01`](https://github.com/qbicsoftware/data-manager-app/issues/1673) ([#1678](https://github.com/qbicsoftware/data-manager-app/issues/1678)), [`FEAT-AUTH-FLOWS-02`](https://github.com/qbicsoftware/data-manager-app/issues/1674) ([#1680](https://github.com/qbicsoftware/data-manager-app/issues/1680)), [`FEAT-AUTH-FLOWS-05`](https://github.com/qbicsoftware/data-manager-app/issues/1677) ([#1683](https://github.com/qbicsoftware/data-manager-app/issues/1683)) |
| **Feature** | [`FEAT-AUTH-FLOWS`](https://github.com/qbicsoftware/data-manager-app/issues/1672) |
| **ADRs** | none — no architectural decision required; rationale is in the script header |
| **Scope** | create 1 table; no existing table altered |
| **Script** | [`v1.20.4/auth-flow-hardening.sql`](v1.20.4/auth-flow-hardening.sql) |
| **Target datasource** | `data_management` |

### What it does

- **`user_verification_token`** — single-use, time-limited tokens for email confirmation
  (`EMAIL_CONFIRMATION`), password reset (`PASSWORD_RESET`) and the one-time set-password invitation
  for ORCID-only accounts (`SET_PASSWORD`). Only a **SHA-256 hash** is stored; the raw token exists
  once, in the outgoing email, and cannot be recovered from the database. Three nullable timestamps
  record how a token stopped being usable: `consumedAt` (used), `supersededAt` (replaced when a
  newer token was issued for the same purpose), or expiry via `expiresAt`.

Issuing a new token for the same purpose **supersedes** the previous one, so two live links can
never coexist for one account.

### ⚠️ Links in flight stop working (decision B1)

This is the one user-visible consequence and it must be communicated, not discovered.

Links already delivered carry the **old** format — `/login?confirm-email={userId}` for confirmation
and `/registration/reset-password?…={userId}` for reset — which the new code no longer accepts.
They stop working **by design**; no dual-mode compatibility path is shipped (decision B1). Any user
holding an old link must request a new one.

Before applying, tell support/helpdesk:

> "After the release, older confirmation and password-reset emails will no longer work. If a user
> reports a dead link, the answer is: request a new link from the login page. Do not ask them to
> resend the original email."


Functional check after the code is deployed: register a user, follow the confirmation link once
(address confirmed), follow it again (rejected). Request a reset link, follow it, set a new password,
follow it again (rejected).

### Rollback

**Do not drop the table to revert this release.** Both new tables are additive and inert without the
code that reads them, so the correct revert is: redeploy the previous application version and **leave
the schema in place**. Nothing else in the 1.20.x schema references them, and no query breaks because
they exist.

Dropping `user_verification_token` is a last resort, and it costs more than it restores:

```sql
-- LAST RESORT ONLY. Read both warnings first.
DROP TABLE IF EXISTS `user_verification_token`;
```

1. **It invalidates every unconsumed link**, including the ones the reverted code cannot reissue — the
   old identifier-based links are gone from the code and are not restored by this. Users must request
   new links, and on the reverted version they cannot.
2. **It destroys the audit trail.** This table is the only record of which links were issued,
   consumed, superseded or expired. Export before dropping — the statement is in the script header.

There is no state, at any point, in which the pre-change links work again. Reverting the code restores
the old behaviour for *new* links only.

### Operator notes

- **Non-destructive.** One new table; no existing table, column, view or index is touched. Safe to
  apply on a live database with the application running.
- **Nothing reads this table until the new application code ships.** Applying the DDL alone changes
  no behaviour — old links keep working until the code deploy.
- **Retention is not decided here.** Consumed rows are kept for audit and are meant to be purged by a
  scheduled job; the retention period is owned by the security and privacy note
  ([#1669](https://github.com/qbicsoftware/data-manager-app/issues/1669)). Until that is settled, do
  not implement a purge — and note that the audit export above may be the only copy.
- **There is no admin or support path to read a token back.** Only hashes are stored. A user who lost
  their link gets a new one; that is the only remedy, and it is what AUTH-R-05 requires.

## Migration #2: Server-side throttling for the auth flows

**Status:** ✅ **approved.** The AGENTS.md §12 sign-off for the `auth_attempt` table was recorded by
the Product Owner — see
[#1690](https://github.com/qbicsoftware/data-manager-app/pull/1690#issuecomment-6847303615). The
approved scope is the creation of `auth_attempt` only: one new table, no existing table altered, no
foreign key.

The script was validated beforehand on a throwaway MariaDB 12.3 instance: it applies twice
idempotently, rolls back cleanly, and the upgrade path from the earlier table shape works (including
adding a missing `windowSeconds` column, which `CREATE TABLE IF NOT EXISTS` would silently skip).

| Field | Value |
|---|---|
| **Story** | [`FEAT-AUTH-FLOWS-03`](https://github.com/qbicsoftware/data-manager-app/issues/1675) ([#1682](https://github.com/qbicsoftware/data-manager-app/issues/1682)) |
| **Feature** | [`FEAT-AUTH-FLOWS`](https://github.com/qbicsoftware/data-manager-app/issues/1672) |
| **ADRs** | none — the design rationale is the script header |
| **Scope** | create 1 table; no existing table altered; **no foreign key** |
| **Script** | [`v1.20.4/auth-attempt-throttling.sql`](v1.20.4/auth-attempt-throttling.sql) |
| **Target datasource** | `data_management` |

### What it does

Creates **`auth_attempt`**, the counter behind server-side throttling for the three unauthenticated
auth flows: `LOGIN`, `EMAIL_CONFIRMATION_RESEND`, `PASSWORD_RESET_RESEND`.

This replaces the 30-second resend lockout in `EmailConfirmationMain`, which was a `java.util.Timer`
over a field in a UI-scoped bean — reloading the page reset it, so it was not a control at all.

### What changes for users

Repeated failed logins, and repeated "resend" requests, are now blocked **server-side** and survive a
reload. The block is temporary.

**The visitor is not told they are throttled.** A throttled login shows the same
"Incorrect username or password" as a wrong password, and a throttled resend shows the same
"check your inbox" panel as a successful one. This is deliberate and is required by `AUTH-NFR-03`: a
distinct "too many attempts" screen would confirm to an attacker that the address they are guessing
at is a real account. **Helpdesk scripts must not promise a specific error message for throttling.**

### ⚠️ Scope decision — account scope only, not origin scope

> **Operators: the proxy requirements live in
> [`docs/operations/installation-and-administration.md`](../../operations/installation-and-administration.md) §1.**
> Read §1.8 for the residual risk described below before you consider enabling
> `server.forward-headers-strategy`.

`AUTH-NFR-03` asks for throttling *per account and per request origin*. **Only account scope ships in
this release.** Origin scope is deferred because the application cannot currently determine a client
address:

- the app runs behind HAProxy, which terminates TLS;
- `server.forward-headers-strategy` is unset, no `RemoteIpValve` is configured, and nothing reads
  `getRemoteAddr()` or `X-Forwarded-For`;
- therefore `getRemoteAddr()` returns the **proxy**.

Keying a bucket on that address would put every user of the deployment into one row, and a single
anonymous attacker filling it would block the entire user population — **a self-inflicted global
denial of service, worse than the gap it closes**.

Doing it correctly requires trusted forwarded headers: a trusted-proxy allowlist, plus HAProxy
**overwriting** rather than appending `X-Forwarded-For` (the header is client-supplied; trusting the
leftmost entry lets an attacker mint a fresh bucket per request). That work is tracked separately and
also unblocks passkeys and the ORCID `{baseUrl}` redirect — see
[the milestone plan](../../plans/MILESTONE-MFA-self-governed-2fa.md) §1a condition 1. It needs **no
schema change**: `scope` is an open `varchar` and `attemptKey` is an opaque hash.

**Residual risk accepted — state this accurately in the release announcement.** Account-scope
throttling stops credential stuffing against a *known target* and stops mail-bombing a *single*
inbox. It does **not** stop one source sending one reset mail to many different addresses — that is
volume/cost abuse, mitigated upstream by the SMTP relay's own rate limits, and it is not account
takeover. It also does not prevent an attacker locking a *specific known victim* out for the block
duration; that is the cost of not having origin scope yet, and it is why the block is temporary.

**In one line:** this release narrows the bulk-abuse exposure; it does not close it. Per-origin
throttling closes it, and that is a separate, proxy-side change.

```sql

-- Rows currently blocked.
```

Functional check: fail a login 11 times (default limit is 10) and confirm the 11th shows the same
"Incorrect username or password" message as the first — **not** a "too many attempts" screen. Then
wait for the block to expire and confirm login works again.

### Rollback

**Do not drop the table to revert this release.** Redeploy the previous application version and leave
the schema in place: the table is inert without the code, and the reverted code never queries it.

```sql
-- LAST RESORT ONLY: the reverted code does not read this table, so there is no reason to drop it.
DROP TABLE IF EXISTS auth_attempt;
```

Should you drop it anyway: it holds no audit trail — it is a rate-limiting counter whose contents are
meaningless without the code that reads it. Dropping it loses only the current block state, so
rolling back re-enables unthrottled attempts, which is the pre-change behaviour rather than a data
loss. No other table references it and it references nothing.

### Operator notes

- **Non-destructive.** One new table; nothing existing is touched.
- **Behaviour change.** If your helpdesk has a script that promises a "too many attempts" message,
  it is now wrong. See *What changes for users*.
- **Holds no personal data beyond an address hash.** `attemptKey` is an opaque hash of the submitted
  address, not the address itself.
- **Retention is deliberately not implemented.** Rows are not pruned in this release, because
  retention is a compliance decision owned by
  [#1669](https://github.com/qbicsoftware/data-manager-app/issues/1669). `lastAttemptAt` is indexed
  so a scheduled sweep can call `JpaAuthAttemptCounter.purgeOlderThan(Instant)`. Until that lands the
  table grows without bound — one row per address that has attempted a login or a resend, so small,
  but unbounded, and recorded here rather than left to be discovered.
- **A deadlock that only appears on MariaDB.** Recorded because it will be hit again by anyone
  simplifying this code: the first implementation reset an elapsed window with a separate
  `UPDATE … WHERE windowStartAt < ?` before the upsert, which deadlocks on real InnoDB under 16
  concurrent attempts on one bucket. It does not reproduce on H2. Fixed by folding the window
  roll-over into the single `INSERT … ON DUPLICATE KEY UPDATE` statement.

## Not in this release — recorded so it is not misread as a gap

### ORCID-only accounts keep working as they are (`FEAT-AUTH-FLOWS-05`, #1683)

`AUTH-R-07` (decision D1b) requires every local account to hold a password. Accounts created through
the ORCID registration path have `encryptedPassword IS NULL`, and **this release does not change
that**. They keep authenticating through ORCID exactly as before.

The backfill is a **procedure**, not a script: a password cannot be generated meaningfully, it must be
*chosen by the person* and arrive through the verified email address, so each affected row needs a
one-time `SET_PASSWORD` invitation token. `user_verification_token` already supports the purpose, so
the follow-up release needs **no schema change** — which is why it is not in this one.

**Do not run a backfill by hand against this release.** The code that issues the invitations ships
with #1683.

If you want to know the size of the affected population, this is read-only and safe:

```sql
SELECT COUNT(*) AS orcid_only_accounts
  FROM users
 WHERE encryptedPassword IS NULL
   AND oidcId IS NOT NULL;
```

### Per-origin throttling (#1691)

Described under migration #2 *⚠️ Scope decision*. Needs HAProxy changes and a trusted-proxy
configuration; not in this repository and not in this release.

## Post-migration checklist

After applying both migrations and deploying v1.20.4:

1. **Schema objects present.**
   - `user_verification_token` exists, `tokenHash` is `char(64)`, FK to `users` cascades.
   - `auth_attempt` exists with `uk_auth_attempt_scope_key`, and **no** foreign keys.
2. **Application starts without errors** — check the logs for unresolved-placeholder, Artemis,
   Flyway/JPA schema-validation, or datasource errors.
   **A startup failure mentioning a verification-token lifetime or a throttle threshold is a
   configuration error, not a bug** — see *Application properties changes*.
3. **Configuration** — confirm the two renamed keys are in use and that no endpoint still points at
   `/login` or the bare `new-password` path.
4. **Smoke test the flows:**
   - register a new account → a confirmation mail arrives → the link confirms **once** and is
     rejected the second time;
   - request a password reset → the link works once → the second use is rejected;
   - open an **old** confirmation or reset mail → it does not work. This is expected (decision B1);
   - fail a login 11 times → the 11th shows "Incorrect username or password", not a throttle screen;
   - click "resend verification link" 4 times → the 4th shows the "already sent / wait N minutes"
     panel, and the block survives a page reload.
5. **Confirm `auth_attempt` is being written** — `SELECT COUNT(*) FROM auth_attempt;` should be
   non-zero after step 4.
6. **Roll the change through your instances.** Sessions are **not** replicated (no `spring-session`,
   no Hazelcast), so during a rolling restart a user may land on a node that does not hold their
   pending-confirmation session state. Vaadin already requires sticky sessions, so if you run more
   than one node, confirm affinity is in place **before** the deploy.
