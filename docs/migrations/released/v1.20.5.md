# Migration: v1.20.5

**Previous version:** 1.20.4
**Target release version:** 1.20.5
**Status:** released

> **To operators:** This document describes the configuration and behaviour changes for
> **Data Manager v1.20.5**, for installations upgrading from v1.20.4.
>
> **There are no schema changes in this release.** No migration script has to be applied, and no
> table, column or index is altered or dropped. The sections below exist because v1.20.5 still
> changes operator-visible behaviour: the mail submission path, the error-notification channel, and
> the availability (but not the activation) of per-origin auth throttling.

For the migration documentation structure, see [`README.md`](../README.md).

## Read this first — what changes for operators

1. **No database work.** Do not run a migration just because this guide exists. The schema at
   v1.20.4 is the schema at v1.20.5.
2. **Per-origin throttling is now implemented, but ships disabled.** The code, configuration keys
   and database representation are present (`auth_attempt` rows with `LOGIN_ORIGIN`, `MAIL_ORIGIN`
   and `REGISTRATION_ORIGIN` scopes). Nothing is enforced per origin until an operator turns it on,
   and turning it on requires a correct reverse proxy first. If you do nothing, authentication
   throttling behaves exactly as in v1.20.4 (account scope only).
3. **Error-notification mail now requires STARTTLS.** The logback appender behind
   `EmailOnError` used logback's `STARTTLS` option, which only *enables* the upgrade and falls back
   to cleartext when the relay does not offer it. It now requires the upgrade. Against a relay that
   cannot do STARTTLS, **no error mail is sent**; the refusal is logged as a send failure. This is
   the same posture v1.20.4 applied to the application's own mail path.
4. **`MAIL_PORT` is now honoured.** `spring.mail.port` was hardcoded to `587` in the shipped
   configuration while `README.md` documented `MAIL_PORT` as configurable, so a deployment on 465
   or 2525 had its setting silently ignored. Both the shipped properties and the distribution
   template now read `${MAIL_PORT:587}`.
5. **A password-reset request no longer retries a failed SMTP submission.** Each retry re-issued
   the token and invalidated the link the previous attempt may already have delivered. The retry
   budget is now zero. A transient SMTP failure therefore leaves the user with no reset mail rather
   than a possible duplicate whose predecessor is dead; the request page already tells the user to
   request another link, and the resend throttle permits three per 15 minutes. Submission failures
   are now logged, which they previously were not.

## Release-wide pre-flight

No database backup is required for this release, because no schema is touched. The checks below are
about the deployment environment, not the database.

1. **Confirm the current version** is the expected baseline (normally 1.20.4). An installation that
   has not received the v1.20.4 tables is not ready for this guide's *Verification* queries.
2. **Check the SMTP relay can upgrade to STARTTLS on the submission port.** A relay that only speaks
   cleartext SMTP will now produce **no error-notification mail**. Test submission before the deploy
   rather than discovering it during the first incident.
3. **Check whether `MAIL_PORT` is set** in the deployment configuration. Until this release it had no
   effect; from this release it does. If it is set to a port the relay does not serve, mail will now
   fail where it previously appeared to work on 587.
   - Port **587** uses STARTTLS submission (the default).
   - Port **465** is implicit TLS and needs `spring.mail.properties.mail.smtp.ssl.enable=true` with
     STARTTLS disabled instead. It is not a drop-in port change.
4. **If you intend to enable origin-scope throttling**, complete the reverse-proxy prerequisites
   first. Do not enable it during the release deploy.

## Configuration changes

### Origin-scope throttling (new keys, all inert by default)

`AUTH-NFR-03` asks for throttling per account **and** per request origin. Account scope shipped in
v1.20.4. This release adds the origin half; see
[ADR 0010](../../adr/0010-trusted-client-identity-behind-reverse-proxy.md) and
[#1691](https://github.com/qbicsoftware/data-manager-app/issues/1691).

**Nothing changes on deploy**, because origin scope ships disabled and the header strategy is
unchanged.

| Key | Default | Meaning |
|---|---|---|
| `qbic.auth-throttle.login.origin.enabled` | `false` | **Single switch for every origin bucket** |
| `qbic.auth-throttle.login.origin.max-attempts` | `60` | Failed logins per origin before the origin block |
| `qbic.auth-throttle.login.origin.window` | `PT15M` | Counting window for the login origin bucket |
| `qbic.auth-throttle.login.origin.block-duration` | `PT10M` | How long a login origin block lasts |
| `qbic.auth-throttle.mail-origin.max-attempts` | `20` | Link resends per origin before the origin block |
| `qbic.auth-throttle.mail-origin.window` | `PT15M` | Counting window for the mail origin bucket |
| `qbic.auth-throttle.mail-origin.block-duration` | `PT15M` | How long a mail origin block lasts |
| `qbic.auth-throttle.registration-origin.max-attempts` | `100` | Registrations per origin before the origin block |
| `qbic.auth-throttle.registration-origin.window` | `PT15M` | Counting window for the registration origin bucket |
| `qbic.auth-throttle.registration-origin.block-duration` | `PT10M` | How long a registration origin block lasts |

> **One switch, three buckets.** `login.origin.enabled` is named after login because that is where the
> work started, but it governs the mail and registration buckets too. A per-flow switch would let a
> deployment be origin-scoped for login and silently account-scoped for the flows that send mail.

**To turn it on** (only after the proxy change below):

```properties
server.forward-headers-strategy=native
qbic.auth-throttle.login.origin.enabled=true
```

**Proxy prerequisite, not a property:** HAProxy must **replace** `X-Forwarded-For`
(`http-request set-header X-Forwarded-For %[src]`). `option forwardfor` alone appends, which leaves
the client's own entry at the front of the list. Setting `enabled=true` with any strategy other than
`native` is a **startup failure**, deliberately. `framework` lets the client choose its own bucket
key; `none` makes one bucket cover the whole deployment. Both are worse than account scope alone.

> **Do not enable this during a release deploy.** It is a separate, independently revertable operator
> step because `server.forward-headers-strategy=native` also changes how absolute links
> (confirmation/reset mail) and the ORCID redirect URI are built. Canary one node first — see
> [`docs/operations/installation-and-administration.md`](../../operations/installation-and-administration.md)
> §1.2, §1.5 and §1.7.

**No schema change is involved.** Origin buckets are additional rows in the existing `auth_attempt`
table with different `scope` values (`LOGIN_ORIGIN`, `MAIL_ORIGIN`, `REGISTRATION_ORIGIN`); `scope`
is an open `varchar` and `attemptKey` is already an opaque hash. Existing rows are untouched and no
backfill is needed.

### Mail port

`spring.mail.port` now resolves `${MAIL_PORT:587}` in both
`datamanager-app/src/main/resources/application.properties` and `application.properties.template`.
The default is unchanged. A deployment that already sets `MAIL_PORT` will see that value take effect
for the first time — check it before deploying.

### Error-notification mail

`spring.mail.*` and `qbic.mail.verify-connection-on-startup` are unchanged. What changes is what the
logback error-notification appender does when the SMTP server will not upgrade to TLS.

| | Before | After |
|---|---|---|
| Relay supports STARTTLS | mail delivered, encrypted | mail delivered, encrypted |
| Relay does **not** support STARTTLS | mail delivered **in cleartext**, credentials on the wire | **nothing sent**; the refusal is reported as a send failure |

This closes the same defect class as v1.20.4's `starttls.required` change on the application's own
mail path — but that release only fixed `spring.mail.properties.*`, which **does not reach logback**.
The error-notification channel kept falling back to cleartext. It now requires TLS via a subclass of
logback's `SMTPAppender`
(`life.qbic.datamanager.logging.StartTlsRequiredSmtpAppender`), since logback offers `starttls.enable`
but no `required`.

**What an operator should check before deploying:**

- The relay must offer STARTTLS on the submission port. A relay that only speaks cleartext SMTP for
  submission will now produce **no error mail at all**.
- This is deliberate and not a fallback: a mail server that cannot encrypt submission is a deployment
  problem to fix. Watch for the startup gate refusing to boot (if
  `qbic.mail.verify-connection-on-startup` is on, which it is by default) — that is the same defect,
  caught earlier.
- Read the trade honestly: error-notification mail is now able to fail silently from a developer's
  perspective. It is not invisible — the failure lands in the application log and in logback's status
  manager — but nobody receives an email saying the email failed. Confirm one error mail arrives after
  the deploy rather than assuming it.

**Known limitation, documented rather than hidden:** the logback appender does not receive
`spring.mail.properties.*`. Only the `spring.mail.*` values named as `<springProperty>` in
`logback-spring.xml` (host, port, username, password) reach it. Adding e.g. `mail.smtp.from` or a
custom timeout to `application.properties` will **not** affect error mail. The TLS requirement is
applied in the appender class, so changing it means editing the class, not the properties file.

## Verification

There is no migration to verify. After deploying:

1. **The application started.** A TLS mismatch on the mail path is a startup failure when
   `qbic.mail.verify-connection-on-startup=true` (the default), so a successful boot already checks
   the application mail path.
2. **Error-notification mail still arrives.** Trigger one error (or use the relay's test facility)
   and confirm the message is received. A relay that cannot upgrade to STARTTLS will report a send
   failure in the log instead.
3. **Mail submission uses the intended port.** If `MAIL_PORT` is set, confirm the relay saw a
   connection on that port. A wrong value is no longer silently ignored.
4. **A password-reset request behaves as documented.** Request one reset and confirm exactly one mail
   arrives. A submission failure should now appear in the log; it is no longer retried.

If you enabled origin-scope throttling, additionally run these checks after a few failed logins on
the canary node:

```sql
-- Which origin buckets exist at all. All three ORIGIN scopes must appear once the corresponding
-- flows are exercised; a flow whose bucket is missing is still account-scoped only, i.e. unbounded.
SELECT scope, COUNT(*) AS rows_
FROM auth_attempt WHERE scope LIKE '%ORIGIN' GROUP BY scope;

-- How many distinct origins are being tracked. A handful is healthy; exactly 1 means the whole
-- deployment is sharing an origin, i.e. getRemoteAddr() is still the proxy -- STOP and roll back.
SELECT COUNT(DISTINCT attemptKey) AS distinct_origins
FROM auth_attempt WHERE scope = 'LOGIN_ORIGIN'
  AND lastAttemptAt > UTC_TIMESTAMP(6) - INTERVAL 15 MINUTE;

-- What is currently blocked, in any bucket.
SELECT scope, attemptCount, blockedUntil FROM auth_attempt
WHERE blockedUntil > UTC_TIMESTAMP(6);
```

The application log must also contain no `no trusted client origin could be resolved` warning. If it
does, the throttle has degraded to account scope and is telling you so.

## Rollback

There is no schema to roll back. To return to the v1.20.4 behaviour, redeploy the v1.20.4 application
code.

- **Origin-scope throttling:** set `qbic.auth-throttle.login.origin.enabled=false` first. If you also
  set `server.forward-headers-strategy=native`, reverting it changes how absolute links and the ORCID
  redirect URI are built, so treat the two changes as one rollback step.
- **Error-notification mail:** reverting restores the cleartext fallback for relays that cannot do
  STARTTLS. That fallback is the defect this release fixed; do not revert it merely to make error
  mail work.
- **`MAIL_PORT`:** if a previously ignored value now points at the wrong port, correct the variable or
  remove it to accept the `587` default.

## Not in this release

These were deferred by previous guides and are still not satisfied. Do not treat their absence from
this guide as a regression.

- **`FEAT-AUTH-FLOWS-05` / #1683 — ORCID-only accounts still have `encryptedPassword IS NULL`.**
  The set-password backfill is a *procedure*, not a script; it needs no schema change because
  `user_verification_token` already carries the `SET_PASSWORD` purpose. Open execution questions are
  in [`v1.20.4.md`](v1.20.4.md) §"Not in this release".
- **#1669 — retention/purge for `user_verification_token` and `auth_attempt`.** Both tables grow
  without bound until it lands.
- **#1691 deployment half — enabling origin-scope throttling.** The code ships in this release, but
  the HAProxy `X-Forwarded-For` replacement and the `native` header strategy are operator actions
  outside this repository, and both stay off by default.
