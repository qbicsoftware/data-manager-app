1. API Contract Reading

  1. Required fields: design, contacts, requestId, and projectCode — the compact constructor calls requireNonNull on each. funding (and offerId) are explicitly allowed to be null; there is no requireNonNull for them.
  2. Safer because funding() may return null directly (documented in its Javadoc), which risks a NullPointerException if the caller does not check. optionalFundingInformation() wraps the value in an Optional, forcing the caller to handle the absent case safely.
  3. Correlation / tracing. In an async/reactive API, responses may not arrive in the same order or may be processed by different threads. The requestId lets the client match a response to its original request and enables distributed tracing and logging across the call chain.
  4. Mono means the result is not immediately available — it will be provided asynchronously later (e.g., after database writes or validation). The client can subscribe to it or compose it with other async operations without blocking the current thread.

2. Validation & Authorization

  1. Failures are blocking errors that prevent the operation. Warnings are non-blocking alerts that the client should see, but the operation can still proceed. allPassed() returns true because it only checks failures.isEmpty() — warnings do not count as failures.
  2. Success: ValidationResult.successful(). With failures: ValidationResult.withFailures(List.of("message")).
  3. Any two of: (a) all return ValidationResult, (b) all are annotated with @PreAuthorize requiring WRITE permission on the Project, (c) all accept a ProjectId parameter, (d) all delegate to a domain-specific validator component rather than containing the rules themselves.
  4. The user must have WRITE permission on the specific Project identified by projectId. If they only have READ permission or no permission, Spring Security will reject the method call before any validation logic runs.
  5. Facade pattern. It provides a single, stable entry point for the UI layer. If the internal validator implementations are refactored (split, merged, or replaced), the UI code that calls MeasurementValidationService does not need to change.

3. Domain Model & Bug Hunt

  1. createSingleMeasurement takes a single NGSSpecificMeasurementMetadata and creates a measurement for one sample. createWithPool takes a Collection<NGSSpecificMeasurementMetadata> and creates a measurement for a pooled sample group. The key business-rule difference: pooled measurements require every metadata entry to have an index present.
  2. Every entry in specificMeasurementMetadata must have an index present (i.e., Optional::isEmpty on the index must be false). If violated, an IllegalArgumentException is thrown with the message: "All specific metadata must have an index in a pooled measurement".
  3. The five mandatory fields checked in validateMandatoryDataRegistration are: measuredSamples (sample IDs), organisationId, instrumentCURIE, facility, and sequencingReadType.
  4. Bug: In the first if/else block of the deprecated validateMandatoryDataForUpdate, the code calls validation.combine(...) but never assigns the result back to validation. It should be validation = validation.combine(...), matching all the later blocks. Because of this, the check for an empty measurementIdentifier is silently discarded — its failure message is lost.
    Fix: Add the missing assignment in the first block.
  5. Two MeasurementUpdatedEvent objects are fired (one per setter call). This is potentially problematic because downstream consumers see two separate update events for what is logically a single multi-field update. It can lead to redundant processing, duplicate audit-log entries, or race conditions if consumers react to each event independently.
